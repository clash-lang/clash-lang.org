Clash 1.10 is out! You can find the full list of changes in the
[CHANGELOG](https://github.com/clash-lang/clash-compiler/blob/master/CHANGELOG.md#1100-apr-23rd-2026),
but I want to use this post to highlight the parts that matter most when moving
an existing design forward.

This is also a personal milestone: I joined [QBayLogic](https://qbaylogic.com/) as the new Clash lead
in January 2026, and Clash 1.10 is the first release made in that role. My immediate focus is to keep Clash
moving in a practical direction: maintaining the compiler, making the ecosystem easier to use, writing great
documentation, and spending engineering time on the places where users currently lose the most time.

## Highlights

Clash 1.10 adds support for GHC 9.12, removes support for GHC 9.4 and older,
and contains a large set of fixes in the compiler and Prelude. A few additions
are worth calling out:

- [`Clash.Class.NumConvert`](https://hackage-content.haskell.org/package/clash-prelude-1.10.0/docs/Clash-Class-NumConvert.html), a new API for safe numeric conversions.
- More time-related domain types in [`Clash.Signal`](https://hackage-content.haskell.org/package/clash-prelude-1.10.0/docs/Clash-Signal.html),
  such as [`Seconds`](https://hackage-content.haskell.org/package/clash-prelude-1.10.0/docs/Clash-Signal.html#t:Seconds),
  [`Milliseconds`](https://hackage-content.haskell.org/package/clash-prelude-1.10.0/docs/Clash-Signal.html#t:Milliseconds),
  [`DomainToHz`](https://hackage-content.haskell.org/package/clash-prelude-1.10.0/docs/Clash-Signal.html#t:DomainToHz),
  [`PeriodToCycles`](https://hackage-content.haskell.org/package/clash-prelude-1.10.0/docs/Clash-Signal.html#t:PeriodToCycles), and
  [`ClockDivider`](https://hackage-content.haskell.org/package/clash-prelude-1.10.0/docs/Clash-Signal.html#t:ClockDivider).
- [`maybeResize`](https://hackage-content.haskell.org/package/clash-prelude-1.10.0/docs/Clash-Class-Resize.html#v:maybeResize)
  and [`maybeTruncateB`](https://hackage-content.haskell.org/package/clash-prelude-1.10.0/docs/Clash-Class-Resize.html#v:maybeTruncateB),
  for resizing while checking whether information would be lost.
- Constant-friendly signal operators such as
  [`(.==)`](https://hackage-content.haskell.org/package/clash-prelude-1.10.0/docs/Clash-Signal.html#v:.-61--61-),
  [`(==.)`](https://hackage-content.haskell.org/package/clash-prelude-1.10.0/docs/Clash-Signal.html#v:-61--61-.),
  [`(.<=)`](https://hackage-content.haskell.org/package/clash-prelude-1.10.0/docs/Clash-Signal.html#v:.-60--61-), and
  [`(.&&)`](https://hackage-content.haskell.org/package/clash-prelude-1.10.0/docs/Clash-Signal.html#v:.-38--38-).
- [`HasField`](https://hackage.haskell.org/package/base/docs/GHC-Records.html#t:HasField)
  support for [`Signal dom r`](https://hackage-content.haskell.org/package/clash-prelude-1.10.0/docs/Clash-Signal.html#t:Signal),
  making record dot access work through signals.
- Several new zero-width related instances, including support for
  [`Index 0`](https://hackage-content.haskell.org/package/clash-prelude-1.10.0/docs/Clash-Sized-Index.html#t:Index)
  in more places.

The rest of this post focuses on the two larger API-level changes: users of
[`Clash.Prelude.DataFlow`](https://hackage-content.haskell.org/package/clash-prelude-1.8.5/docs/Clash-Prelude-DataFlow.html)
must move to `clash-protocols`, and porting code may need small type fixes.

## From [`Clash.Prelude.DataFlow`](https://hackage-content.haskell.org/package/clash-prelude-1.8.5/docs/Clash-Prelude-DataFlow.html) to `clash-protocols`

The deprecated [`Clash.Prelude.DataFlow`](https://hackage-content.haskell.org/package/clash-prelude-1.8.5/docs/Clash-Prelude-DataFlow.html)
module has been removed in Clash 1.10.
If you still depend on it, the recommended replacement is
[`clash-protocols`](https://github.com/clash-lang/clash-protocols).

This is more than a module rename. [`Clash.Prelude.DataFlow`](https://hackage-content.haskell.org/package/clash-prelude-1.8.5/docs/Clash-Prelude-DataFlow.html)
was great for what it did, but we found that there were severe limitations in
the way it worked.
`clash-protocols` is a ground-up rethink of how to handle protocols in Clash.

People who actively follow the Clash ecosystem may know that this package
has existed in an unreleased state for a few years already. We finally feel comfortable
releasing it, as it has seen extensive usage in large Clash projects such as [Bittide](https://github.com/bittide/bittide-hardware).

If you are a user of [`Clash.Prelude.DataFlow`](https://hackage-content.haskell.org/package/clash-prelude-1.8.5/docs/Clash-Prelude-DataFlow.html)
and have not moved to `clash-protocols`,
please take the time to read the [`README`](https://github.com/clash-lang/clash-protocols/blob/main/README.md).
The [`Df`](https://hackage-content.haskell.org/package/clash-protocols-0.1/docs/Protocols-Df.html) protocol will be of particular interest to you.

## `NumConvert`

A release highlight is [`Clash.Class.NumConvert`](https://hackage-content.haskell.org/package/clash-prelude-1.10.0/docs/Clash-Class-NumConvert.html).
Haskell programmers usually reach for
[`fromIntegral`](https://hackage.haskell.org/package/base/docs/Prelude.html#v:fromIntegral)
when converting between number types, but in Clash that can hide two different
issues.

First, [`fromIntegral`](https://hackage.haskell.org/package/base/docs/Prelude.html#v:fromIntegral) goes through
[`Integer`](https://hackage.haskell.org/package/base/docs/Prelude.html#t:Integer);
in generated HDL, Clash currently represents
[`Integer`](https://hackage.haskell.org/package/base/docs/Prelude.html#t:Integer)
and
[`Natural`](https://hackage.haskell.org/package/base/docs/Numeric-Natural.html#t:Natural)
as 64-bit values. That means a conversion such as
[`Unsigned`](https://hackage-content.haskell.org/package/clash-prelude-1.10.0/docs/Clash-Sized-Unsigned.html#t:Unsigned)
`96 ->`
[`Unsigned`](https://hackage-content.haskell.org/package/clash-prelude-1.10.0/docs/Clash-Sized-Unsigned.html#t:Unsigned)
`128` can silently lose bits in hardware even though simulation looks fine.
Second, [`fromIntegral`](https://hackage.haskell.org/package/base/docs/Prelude.html#v:fromIntegral)
allows conversions that cannot represent every input value, such as
[`Signed`](https://hackage-content.haskell.org/package/clash-prelude-1.10.0/docs/Clash-Sized-Signed.html#t:Signed)
`8 ->`
[`Unsigned`](https://hackage-content.haskell.org/package/clash-prelude-1.10.0/docs/Clash-Sized-Unsigned.html#t:Unsigned)
`8`.

[`NumConvert`](https://hackage-content.haskell.org/package/clash-prelude-1.10.0/docs/Clash-Class-NumConvert.html#t:NumConvert)
makes the safe case explicit through
[`numConvert`](https://hackage-content.haskell.org/package/clash-prelude-1.10.0/docs/Clash-Class-NumConvert.html#v:numConvert):

```haskell
numConvert :: NumConvert a b => a -> b
```

If every value of the input type fits in the output type, the conversion
typechecks. If not, use the checked version,
[`maybeNumConvert`](https://hackage-content.haskell.org/package/clash-prelude-1.10.0/docs/Clash-Class-NumConvert.html#v:maybeNumConvert),
with a
[`MaybeNumConvert`](https://hackage-content.haskell.org/package/clash-prelude-1.10.0/docs/Clash-Class-NumConvert.html#t:MaybeNumConvert)
constraint:

```haskell
maybeNumConvert :: MaybeNumConvert a b => a -> Maybe b
```

This deserves more space than a release announcement can give it. A dedicated
[`NumConvert`](https://hackage-content.haskell.org/package/clash-prelude-1.10.0/docs/Clash-Class-NumConvert.html#t:NumConvert)
blog post is already in preparation, and will dig into the motivation, the
design, and how to add support for your own numeric types.

## Porting notes

Most code should move to Clash 1.10 without major changes, but there are two
type-level changes worth checking deliberately.

### `Index` bit width

The bit width of [`Index`](https://hackage-content.haskell.org/package/clash-prelude-1.10.0/docs/Clash-Sized-Index.html#t:Index)
`n` is now defined using
[`CLogWZ 2 n 0`](https://hackage-content.haskell.org/package/ghc-typelits-extra-0.5.3/docs/GHC-TypeLits-Extra.html#t:CLogWZ)
instead of
[`CLog 2 n`](https://hackage-content.haskell.org/package/ghc-typelits-extra-0.5.3/docs/GHC-TypeLits-Extra.html#t:CLog).
[`CLogWZ`](https://hackage-content.haskell.org/package/ghc-typelits-extra-0.5.3/docs/GHC-TypeLits-Extra.html#t:CLogWZ)
is a version of
[`CLog`](https://hackage-content.haskell.org/package/ghc-typelits-extra-0.5.3/docs/GHC-TypeLits-Extra.html#t:CLog)
that is well defined for zero.
[`CLog 2 0`](https://hackage-content.haskell.org/package/ghc-typelits-extra-0.5.3/docs/GHC-TypeLits-Extra.html#t:CLog)
does not reduce, whereas
[`CLogWZ 2 0 0`](https://hackage-content.haskell.org/package/ghc-typelits-extra-0.5.3/docs/GHC-TypeLits-Extra.html#t:CLogWZ)
reduces to `0`. The practical reason is zero-width support:
[`Index 0`](https://hackage-content.haskell.org/package/clash-prelude-1.10.0/docs/Clash-Sized-Index.html#t:Index)
now has a well-defined bit size and a wider set of instances.

Code that manually mirrored the old implementation may need to change:

```haskell
-- Before
type IndexWidth n = CLog 2 n

-- After
type IndexWidth n = CLogWZ 2 n 0
```

### `ghc-typelits-natnormalise`

A [fix](https://github.com/clash-lang/ghc-typelits-natnormalise/commit/c994419b8ad3f6c3c8bb21150ae4e11c5183957a)
in `ghc-typelits-natnormalise` can expose type errors in code that previously typechecked by accident.
The plugin used to unify under non-injective type families. In other words, from a constraint like:

```haskell
CLog 2 n ~ CLog 2 q
```

it could conclude:

```haskell
n ~ q
```

That conclusion is not valid.
[`CLog`](https://hackage-content.haskell.org/package/ghc-typelits-extra-0.5.3/docs/GHC-TypeLits-Extra.html#t:CLog)
is not injective: different inputs can have the same result. For example:

```haskell
type CLogThree = CLog 2 3  -- 2
type CLogFour  = CLog 2 4  -- 2
```

but `3` and `4` are still different type-level naturals.

So code relying on the plugin to recover `n ~ q` from a non-injective type family result may
now fail to typecheck. The fix is often to add type annotations, or to manually show
that the given `n` and `q` are equal.
